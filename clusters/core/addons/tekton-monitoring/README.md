# tekton-monitoring

![Version: 0.1.0](https://img.shields.io/badge/Version-0.1.0-informational?style=flat-square) ![Type: application](https://img.shields.io/badge/Type-application-informational?style=flat-square) ![AppVersion: 0.1.0](https://img.shields.io/badge/AppVersion-0.1.0-informational?style=flat-square)

Observability for the Tekton stack — ServiceMonitors scraping the native Pipelines/Triggers/Results metrics endpoints and the KRCI Tekton analytics Grafana dashboards

Observability for the Tekton stack installed by the `tekton` add-on. Two halves:

1. **ServiceMonitors** pointing kube-prometheus-stack at the metrics endpoints that Tekton
   Pipelines, Triggers, Results and every EventListener already expose. Nothing has to be
   enabled on the Tekton side for the endpoints themselves — the shipped `config-observability`
   already exports to Prometheus. One monitor covers all EventListeners cluster-wide, because
   KRCI EventListeners live in the per-tenant delivery namespaces rather than in
   `tekton-pipelines`.
2. **Grafana dashboards** — pipeline overview, task analytics, queue and scheduling,
   EventListener traffic, platform health and resource consumption. They ship as ConfigMaps and
   are discovered by the kube-prometheus-stack Grafana sidecar (`searchNamespace: ALL`), so they
   work from this add-on's namespace.

## Requirements

- **prometheus-operator** (CRDs for `ServiceMonitor`) and **kube-prometheus-stack** with its
  Grafana sidecar enabled.
- `serviceMonitor.additionalLabels` must match what the cluster's Prometheus selects on.
  kube-prometheus-stack defaults `serviceMonitorSelectorNilUsesHelmValues: true`, which limits
  Prometheus to ServiceMonitors carrying its release label. If the label does not match,
  Prometheus ignores the monitors silently and every panel stays empty.
- The dashboards assume the Prometheus datasource UID is `prometheus`, which is the
  kube-prometheus-stack default. If the cluster overrides `grafana.sidecar.datasources.uid`,
  change `DS` in `generate.py` and regenerate.

## Tekton settings this depends on

The `tekton` add-on already sets these in `config-observability`, so a standard install needs
nothing. Re-apply them if that manifest is re-vendored, or if Tekton comes from another source:

| Key | Set to |
|-----|--------|
| `metrics.count.enable-reason` | `true` |
| `metrics.running-pipelinerun.level` | `pipeline` |

## Editing the dashboards

The JSON under `files/` is generated by `generate.py`. Edit the generator and re-run it, then
commit both — do not hand-edit the JSON:

```sh
python3 generate.py
```

## Values

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| dashboards.enabled | bool | `true` | Ship the Tekton analytics Grafana dashboards as ConfigMaps |
| dashboards.folder | string | `"KRCI"` | Grafana folder the dashboards are filed under (sidecar folderAnnotation) |
| dashboards.label | string | `"grafana_dashboard"` | Grafana sidecar discovery label (kube-prometheus-stack default: grafana_dashboard=1) |
| dashboards.labelValue | string | `"1"` | Value of the discovery label |
| dashboards.list | list | `["tekton-pipeline-overview","tekton-task-analytics","tekton-queue-scheduling","tekton-eventlistener-traffic","tekton-platform-health","tekton-resource-consumption"]` | Dashboards to install. Each entry maps to files/<name>.json. |
| serviceMonitor.additionalLabels | object | `{"release":"kube-prometheus"}` | Labels that let Prometheus select these monitors. kube-prometheus-stack defaults `serviceMonitorSelectorNilUsesHelmValues: true`, which restricts Prometheus to ServiceMonitors carrying its own release label — without a match it silently ignores them and every panel stays empty. Set this to the kube-prometheus-stack release name, or clear it if that cluster sets `serviceMonitorSelectorNilUsesHelmValues: false`. |
| serviceMonitor.enabled | bool | `true` | Create ServiceMonitors for the Tekton components (requires prometheus-operator) |
| serviceMonitor.eventListeners.allNamespaces | bool | `true` | Discover EventListeners in every namespace. KRCI EventListeners live in the per-tenant delivery namespaces, not in tekton-pipelines, so this must stay cluster-wide. |
| serviceMonitor.eventListeners.enabled | bool | `true` | Scrape every EventListener sink (request rate, latency, triggered resources). One monitor covers all of them: the EventListener controller labels each `el-*` Service with `app.kubernetes.io/managed-by: EventListener`. |
| serviceMonitor.eventsController | bool | `true` | Scrape the Pipelines events controller (CloudEvents emission) |
| serviceMonitor.interval | string | `"30s"` | Scrape interval applied to every endpoint |
| serviceMonitor.namespace | string | `"tekton-pipelines"` | Namespace holding the Tekton control plane Services |
| serviceMonitor.pipelinesController | bool | `true` | Scrape the Pipelines controller (pipelinerun/taskrun duration, running counts, throttling, reconciler + workqueue metrics) |
| serviceMonitor.resultsApi | bool | `true` | Scrape the Tekton Results API (gRPC server metrics) |
| serviceMonitor.resultsWatcher | bool | `true` | Scrape the Tekton Results watcher (PipelineRun/TaskRun archival and deletion counters) |
| serviceMonitor.triggersController | bool | `true` | Scrape the Triggers controller (reconciler metrics for EventListener/Trigger resources) |
